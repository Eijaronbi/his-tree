3D BROWSER GAME ON PATCH.GG - CONTEXT FOR THE GAME DESIGNER
=====================================================================
Prepared 12 Nov 2026 | Built by an AI coding agent inside an InstaBox
Linux VM (Debian 13, x86_64, 4 vCPU / 8 GB) | Publisher: patch.gg

THIS IS A 3D GAME. Everything below is 3D: 3D characters, 3D worlds,
3D models remodelled in Blender inside the VM. 2D is used only for the
cover image, logo and small UI icons.

---------------------------------------------------------------------
0. HOW THIS IS BUILT (read this first)
---------------------------------------------------------------------
Everything happens inside one Linux VM. Nothing is done on a phone.

  1. DESIGN - this document. A designer (ChatGPT) writes the spec.
  2. MODELLING - all 3D modelling happens in the VM with Blender 4.3.2
     running headless, driven by Python scripts:
       - import a base character GLB from the patch.gg asset library
       - re-proportion the body, reshape the head, swap hair / clothes /
         armour / weapons from library kits
       - recolour and retexture materials
       - retarget or rebuild the rig, author new clips if needed
       - export an optimised GLB (gltf-transform: meshopt/Draco, WebP
         textures, unused animation clips stripped)
  3. GAME - three.js in the browser, one static web app.
  4. PUBLISH AS OURS - the remodelled characters are published as our
     own patch.gg projects of kind "character" / "asset", with our own
     licence and the original author's credit line preserved plus a
     "modified by us" note. The game itself is published as our own
     project.
  5. COVER ART - Patch generates free covers from the game's own
     screenshots (12 takes, 4 fixes); AI image generation makes the
     key art, logo and UI icons.
  6. LIVE - commit, release, upload, Patch file checks, automated
     play-test on the creator's Windows Patch Desktop (hidden muted
     window), agent reviews the footage, creator approves, Patch's
     scan, game is live on patch.gg.

---------------------------------------------------------------------
1. THE PLATFORM: patch.gg
---------------------------------------------------------------------
* patch.gg is where coding agents make and publish browser games and
  mods. Browser games play in the browser on patch.gg (no install, no
  Windows needed by players). Mods play in the Windows app Patch
  Desktop and need a host game patch.gg already lists.
  THIS PROJECT IS A BROWSER GAME - no mod, no host game.
* Every project is a git repo (public by default, remixable), or it can
  take GitHub as its home.
* A browser game release needs NO recipe: the game opens at index.html
  in the project root. A recipe (JSON: host games, loaders, components,
  paths, settings, tests) exists only for mods.
* Hard limits and rules:
    - Maximum 500 MB per release; we target well under that.
    - No secrets in the repo or release. Patch scans and rejects.
    - No native binaries, no server-side code in a browser game.
    - A cover image is required before a game goes live (free covers
      available, generated from the game's own stills).
    - CC-BY assets must keep their exact credit line.
    - Single-player static hosting is the target. Multiplayer needs a
      separate backend we host ourselves; not part of the release.
    - WebGL2 on a normal desktop browser. Fast load, low draw calls.
    - Keyboard + mouse primary; touch is a bonus, not required.
    - Progress and saves live in the browser (localStorage).
    - The game must be legible in the first 10 seconds: title screen,
      one-line objective, controls on screen.
    - Every third-party asset is credited in a credits screen and in
      the repo README, with the exact credit line from the asset record.

5. WHAT CAN BE ACHIEVED IN 3D HERE
---------------------------------------------------------------------
Realistic for a first release:
  * Third-person, first-person or fixed isometric camera, three.js.
  * A custom hero remodelled from a base above, with real authored or
    reused clips (idle, walk, sprint, jump, attack, hit, death).
  * Melee, ranged and magic combat out of the box, because the KayKit
    characters already carry ~140 clips including 1H/2H attacks, blocks,
    dual wield, bow aiming/draw/release, magic cast/summon, dodges.
  * Enemy archetypes from KayKit skeletons or Kenney characters,
    recoloured and re-rigged, code-driven locomotion.
  * Levels from Kenney kits, Poly Haven and ambientCG props, ambientCG
    materials, Poly Haven HDRIs for sky and lighting.
  * Full loops: wave survival, arena score attack, collect-the-items,
    time trial, puzzle rooms, exploration with objectives, tower
    defence, twin-stick combat, boss fight from a scaled base.
  * Interaction verbs the clips already support: pick up, throw, use
    item, interact, sit, drive.
  * HUD, menus, inventory, dialogue, settings, pause, results screen.
  * Library music + SFX, plus WebAudio-synthesised SFX if needed.
  * localStorage saves, unlocks, difficulty ramp.
  * Cover art and key art generated free by Patch and by AI.
  * Publishing to patch.gg with the full automated test loop.

Possible but riskier / needs a decision:
  * Multiplayer (our own backend, hosted by us, not in the release).
  * Ragdolls and soft-body physics.
  * Very large open worlds (we keep levels compact instead).
  * Vehicle gameplay (KayKit has a "drive" clip, but no rigged vehicle
    cockpit; needs extra modelling).
  * KayKit GLBs are 3.7 MB each with ~140 clips: we strip unused clips
    and optimise, otherwise the game gets heavy fast.

Not possible in this setup:
  * Native plugins, PC-only builds, per-player accounts, anything
    needing a secret in the client.

6. STYLE PRESETS THE AGENT CAN DELIVER RELIABLY
---------------------------------------------------------------------
A) Stylised low-poly cartoon - Kenney mini / blocky look. Cheapest,
   fastest to polish, 30-32 clips each. Platformers, arenas, cute toys.
B) Stylised fantasy - KayKit Adventurers + Skeletons, Poly Haven
   environments, ~140 clips each. RPG-lite, dungeon crawl, survival.
C) Voxel / blocky - Kenney blocky characters + voxel props. Survival
   craft, tower defence, sandbox building.
D) Realistic human - MPFB base remodelled in Blender (face, body, hair,
   clothes), clips authored from scratch. Heaviest; most work.
E) Sci-fi hard-surface - Amazon Berkeley Objects / SimReady panels and
   props, custom-built player character. Arena combat, vehicles.

Pick ONE for the first release and stay inside it.

7. YOUR TASK: RETURN A 3D GAME SPECIFICATION
---------------------------------------------------------------------
Write the spec so a coding agent can build it without asking follow-up
questions. Return exactly these sections:

1. TITLE + one-sentence pitch + a 3-6 word genre tag.
2. PLAYER FANTASY - who the player is and why it is fun, one sentence.
3. CORE LOOP - the repeating cycle of actions.
4. MOMENT-TO-MOMENT - what happens every 5-10 seconds: input, response,
   feedback (sound, camera, hit flash, particles, UI).
5. CAMERA + CONTROLS - third person / first person / fixed isometric;
   full key map; mouse behaviour; mouse-look vs click-to-move; touch
   support yes/no.
6. PLAYER CHARACTER - species, body, clothing, silhouette, colour
   palette (hex), WHICH base from section 3 to remodel and exactly what
   to change (proportions, gear, materials, rig, clips).
7. ENEMIES / NPC CAST - 2-4 types: silhouette, behaviour, how many on
   screen at once, which base each uses, what to recolour.
8. WORLD - level size in metres, layout, landmarks, props, lighting,
   HDRI, time of day, colour palette (hex).
9. OBJECTIVES + PROGRESSION - win condition, lose condition, score,
   difficulty curve over 5-10 minutes, unlocks.
10. HUD + MENUS - exact on-screen elements and positions, and the menu
    flow (title -> how to play -> game -> pause -> game over -> results).
11. AUDIO - music mood, key SFX list, library vs synthesised.
12. ASSET WISH LIST - table: asset id (or description if remodelled),
    purpose, what to change. 15-30 assets maximum.
13. TECH PLAN - three.js approach, scene structure, how characters are
    driven (AnimationMixer clips vs procedural), collision approach,
    performance budget (draw calls, model size, texture sizes), repo
    file layout (index.html, src/, assets/models/, assets/textures/...).
14. MVP vs STRETCH - what ships first, what is deferred.
15. RISKS - the 3 things most likely to break this and the cheapest
    mitigation for each.

Rules:
  * 3D, browser, single-player, desktop keyboard + mouse.
  * Stay inside one style preset from section 6.
  * Fun and legible in the first 10 seconds.
  * Every mechanic must be implementable with the assets and tools
    listed above.
  * No art that must be hand-painted: all 3D comes from the library or
    from remodelling a library base in Blender; AI art is only for the
    cover, logo and UI icons.
  * Be specific. Numbers, names and ids beat adjectives.
